# Profile Notes & Moderation — Scoping

Scoping pass for Profile Social Scoping & Maintenance — Leg 1. Question:
should profile teams get a freeform notes field on the public profile page,
and if so what moderation model applies — same decide-first pattern as
Scoping Sweep Leg 3's public-team-database question (see
`docs/investigations/public-team-browse-upload-scope.md`). Research/decision
only — no implementation.

## What exists today

- **A freeform `notes` field already exists on `Team` — but it's private.**
  `types/pokemon.ts`'s `Team.notes?: string` is a user-editable freeform
  text field (`TeamCard.tsx`'s notes textarea), synced across a user's own
  devices via the existing per-account Worker. It's personal/strategy text
  (the kind of thing a player jots down about a matchup or a build choice),
  not something generated by this app.
- **The public profile endpoint never exposes it.** `worker/src/
  publicProfile.ts`'s `PublicTeam` interface and `extractPublicTeam` only
  forward `id`/`name`/`format`/`visibility`/`pokemon` — `notes` isn't in the
  shape at all, regardless of a team's `visibility` tier.
- **This was a deliberate, already-decided scope boundary, not an
  oversight.** `docs/investigations/public-profiles-safety-filter-research.md`
  (Public Profiles & Team Sharing milestone) explicitly scoped the safety
  filter to exactly three public-facing surfaces: usernames, public team
  names, and public Pokémon nicknames. Notes weren't a fourth surface that
  leg forgot — they were never in scope for public exposure in the first
  place, so no filter was ever needed for them.
- **The existing filter precedent (name vs. nickname) already covers how a
  new freeform field would need to be handled if added.** `extractPublicTeam`
  drops a whole team if its `name` fails `safetyFilter.ts`'s
  `containsDisallowedContent`, but only drops the one field (keeps the rest
  of the Pokémon) if a `nickname` fails — nickname is auxiliary per-slot
  flavor text, not identity-defining the way a team's name is. A public
  `notes` field would be the same shape of auxiliary text as nickname, not
  like name.

## Options considered

**Expose `notes` on the public profile, filtered like nickname (drop the
field on a flag, keep the rest of the team).** The cheapest version to build
— reuses `safetyFilter.ts` exactly as already wired for nicknames, no new
infrastructure, no new moderation category. Rejected anyway: see below.

**Add a separate public-only notes/description field, distinct from the
private `notes`.** Would avoid the privacy mismatch (below) by giving users
an explicit "write something for visitors" field instead of reinterpreting
their private one. Still rejected for the same no-demand reason as the
option above — this is a bigger ask (a new field, new UI, new filter wiring)
for the same unconfirmed demand.

**Leave `notes` private-only, as it is today.** Chosen — see Decision.

## Why this isn't just "add it, it's cheap"

Unlike the public-team-database question, this one *is* cheap to build —
it's one more field on an exposure boundary that already exists, filtered
the same way nickname already is, not a new centrally-hosted service. The
reason to not-build isn't infrastructure risk this time, it's a **privacy
mismatch**: `notes` is personal strategy/matchup text a player writes for
themselves, under an implicit private-by-default expectation that predates
public profiles entirely (the field existed before Public Profiles & Team
Sharing shipped). A team's `visibility` tier was scoped (Teamsheet Open/
Closed Visibility Tiers) around how much of the *competitive set* to show a
visitor — it was never framed as "and also publish whatever I privately
jotted down about this team." Silently starting to publish that text the
next time a user flips a team to `open`/`closed` would surprise anyone who
wrote something in that field before public profiles existed, or who writes
in it today without reading this scoping doc.

There's also no demand signal: nobody has asked for public-facing notes:
this question was generated by the scoping sweep pattern, not a user
request.

## Decision

**Not building this.** `notes` stays a private, per-account-synced-only
field — no public exposure, and therefore no moderation model needed for it.
Reasons:

- It would publish freeform personal text users wrote under a private-by-
  default expectation, the moment they opt a team into a visibility tier
  that was scoped around competitive-set exposure, not notes exposure — a
  silent scope change to a field's meaning, not something a visibility
  toggle should do as a side effect.
- No demand signal — nobody has asked for this; it surfaced from the
  scoping sweep, not a request.
- Unlike the public-team-database question, cost isn't the blocker here (it
  would be cheap — see above) — so this isn't a "wait until it's cheaper"
  deferral, it's a real no.

If real demand for a visitor-facing notes/description shows up later, the
minimum viable version is a **new, separate, opt-in field** (not a reuse of
private `notes`) — written with an explicit "this is what visitors will
see" framing, filtered the same way `nickname` already is (drop the field on
a `safetyFilter.ts` flag, don't exclude the whole team). That's a fresh
scoping pass for whenever that demand is real, not a re-read of this one.
