## TeamCard Paste Team: Pasted Card Jumps Before Re-sort — Leg 1 — 2026-10-17

Two compounding causes. (1) `utils/teamPaste.ts::buildPastedTeam`'s
`...pasted` spread carried over the source team's `sortOrder` verbatim, so
`teamSort.ts`'s tiebreaker treated the pasted card as tied specifically with
the team it was copied from instead of untied like a fresh import - fixed
by explicitly clearing `sortOrder` there. That surfaced a second,
pre-existing bug live: once untied, the card correctly rendered at the
front of its group but ~3s later jumped to the bottom of the whole list -
`useTeams.ts::applySyncedState`'s `reconciled` array built its base order
from the sync response (`records`) rather than local order, so any
locally-added team the response didn't know about yet (a paste, a fresh
import, any `addTeam`) got appended after everything else on the very next
auto-sync round-trip. Fixed by rebuilding `reconciled` from
`teamsRef.current` (local order) instead, merging in the synced version per
id only where it's newer, and appending only genuinely remote-only records
(synced from another device) at the end. This closes the same bug
separately tracked as TODO.md's "applySyncedState Reconciliation Loses
Local-Only Team's List Position" (removed from TODO.md, not actually
cosmetic/self-correcting as first thought). Regression tests added to
`teamPaste.test.ts` and `useTeams.test.ts`. Verified live by the user across
multiple paste attempts after both fixes landed. See commits `679abed`
(sortOrder) and `a506542` (applySyncedState base order).

## TeamCard Notes: Data Loss on First Blur After Expand — Leg 2 — 2026-10-17

`/leg-review` on Leg 1's fix below found it left the same blind-overwrite
shape open for a different race: `applySyncedState`'s `reconciled` list
fell back to `remote` for any id missing from `localById`, which also
matches a team deleted locally (via `deleteTeam`) after the push snapshot
was taken but before the response landed - so the deleted team got put
back, and the unconditional `tombstonesRef.current = []` on the same
success path threw away the tombstone that would've told the server about
the deletion on the next sync. Fixed by giving `applySyncedState` a second
argument, `pushedTombstones` (the tombstone list `useSync.ts`'s push
actually sent, snapshotted before `pushSyncData`): any `records` entry
still carrying a pending local tombstone is dropped instead of falling back
to `remote`, and only tombstones named in `pushedTombstones` get cleared.
Also updated `UseTeamsReturn.applySyncedState`'s doc comment, stale since
Leg 1 (still described a blind overwrite). New regression test in
`useTeams.test.ts`; full trail in
`docs/investigations/teamcard-notes-sync-race.md`. Not manually verified
live - same reasoning as Leg 1, this is a queue-ordering race unit tests
cover more reliably than a live repro. See commit `f17db5b`.

## TeamCard Notes: Data Loss on First Blur After Expand — Leg 1 — 2026-10-17

Root cause wasn't the card-expand animation or the `prevPropNotes`/
`localNotes` resync pattern in `TeamCard.tsx` (both initial suspects, ruled
out) - it was `useSync.ts`'s debounced auto-sync racing a local edit.
Any team mutation schedules a push 5s later; if Notes is typed and blurred
after that but before the push's response lands, `useTeams.ts
::applySyncedState` blindly overwrote local state with the stale pre-edit
snapshot once the response arrived, discarding the just-saved edit even
though it had already won the `enqueueMutation` queue. Full trail,
including why scripted repro attempts against the expand animation came
back clean, in `docs/investigations/teamcard-notes-sync-race.md`. Fixed by
having `applySyncedState` keep whichever side (local vs. synced) has the
newer `updatedAt` per team, plus keep any local-only team the sync response
doesn't know about yet - same flaw, would otherwise drop a brand-new team
instead of just a field. Two new regression tests in `useTeams.test.ts`;
`/leg-review` on this fix separately found a related delete-race flaw,
fixed as Leg 2 above. Verified live across several expand/type/blur cycles
plus a deliberate race-window repro (mutate to reset the 5s debounce, then
type+blur Notes before it fires) against disposable test teams. See commit
`d0fa35a`.

## Dev Environment: Electron Zoom-Persistence Fix + Mobile Web Preview Script — 2026-10-17

Electron zoom fix and the new `npm run dev:mobile` script both landed
2026-10-16 (see `docs/archive/completed-2026-10-16-to-2026-10-16.md`'s
boundary and commits `46513fe`/`b01327a`), but `dev:mobile` itself hadn't
been live-verified yet. Doing so today caught two real bugs: Node 24 on
Windows throws `spawn EINVAL` self-starting Vite through the bare `npx.cmd`
shim without `shell: true` (fixed by spawning `node` directly against
Vite's `bin/vite.js` instead, which also avoids `shell: true`'s own problem
of wrapping the real process in a `cmd.exe` that the script's `child.kill()`
cleanup can't reach); and this machine has no system Chrome installed at
all, so `channel: 'chrome'` always failed (fixed with a fallback to a
locally installed Opera GX, Vanny's actual daily browser, via
`executablePath` resolved through `%LOCALAPPDATA%`). Fixing the Chrome
fallback also exposed a cleanup-ordering bug: a failed browser launch left
the self-started Vite server orphaned on :5174 because `cleanup()` was
defined after the throwable launch call; moved its registration earlier and
wrapped the browser/page logic in `try`/`finally`. Confirmed live end to
end afterward: self-starts `dev:web`, opens a correctly phone-proportioned
Opera GX window, and cleanly tears down the self-started Vite server on
exit. See commit `79992b0`.
